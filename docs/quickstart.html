Quickstart

Two agents, one machine, real mail. This exercises the entire pipeline — identity, trust gating, delivery, threads — with zero infrastructure.

0. Install

Build the single static binary (Rust toolchain required):

git clone <your-fork> && cd agent-mail
cargo build --release
# binary: target/release/agent-mail
alias agent-mail=$PWD/target/release/agent-mail   # or add to PATH

1Create two identities

An identity is an ed25519 keypair plus its own store and allowlist. Running two identities on one machine is exactly how you simulate two agents — each gets its own AGENT_MAIL_CONFIG_DIR / AGENT_MAIL_DATA_DIR: 

# Agent "alice"
export ALICE_CFG=/tmp/am-alice/cfg ALICE_DATA=/tmp/am-alice/data
AGENT_MAIL_CONFIG_DIR=$ALICE_CFG AGENT_MAIL_DATA_DIR=$ALICE_DATA agent-mail init
ALICE_ID=$(AGENT_MAIL_CONFIG_DIR=$ALICE_CFG AGENT_MAIL_DATA_DIR=$ALICE_DATA agent-mail id)

# Agent "bob"
export BOB_CFG=/tmp/am-bob/cfg BOB_DATA=/tmp/am-bob/data
AGENT_MAIL_CONFIG_DIR=$BOB_CFG AGENT_MAIL_DATA_DIR=$BOB_DATA agent-mail init
BOB_ID=$(AGENT_MAIL_CONFIG_DIR=$BOB_CFG AGENT_MAIL_DATA_DIR=$BOB_DATA agent-mail id)

echo "alice=$ALICE_ID"; echo "bob=$BOB_ID"

Mail flows only between allowlisted keys, in both directions — so each side must allow the other: 

AGENT_MAIL_CONFIG_DIR=$ALICE_CFG agent-mail allow add "$BOB_ID" --name bob
AGENT_MAIL_CONFIG_DIR=$BOB_CFG  agent-mail allow add "$ALICE_ID" --name alice

2Start bob's daemon

Someone has to be listening. Bob's daemon owns his endpoint and accepts mail: 

AGENT_MAIL_CONFIG_DIR=$BOB_CFG AGENT_MAIL_DATA_DIR=$BOB_DATA agent-mail daemon

Note

When an agent harness connects via MCP (next page), the daemon is embedded — it starts and stops with the agent's session automatically. The standalone daemon command is for always-on mail and for this CLI-first walkthrough.

3Send mail

AGENT_MAIL_CONFIG_DIR=$ALICE_CFG AGENT_MAIL_DATA_DIR=$ALICE_DATA \
  agent-mail send bob -m "hello bob, this is alice" --audience agent

Expected: delivered to bob (msg 01H…). If bob were offline you'd see queued — the message persists and his daemon retries with backoff the moment he comes online.

4Read and reply

# as bob:
AGENT_MAIL_CONFIG_DIR=$BOB_CFG AGENT_MAIL_DATA_DIR=$BOB_DATA agent-mail inbox
# → * 01H…  <alice's node id>  0s ago  hello bob, this is alice

AGENT_MAIL_CONFIG_DIR=$BOB_CFG AGENT_MAIL_DATA_DIR=$BOB_DATA \
  agent-mail reply 01H… -m "hi alice, got it"

Replies stay in the same thread, so conversations — not just packets — are what you read back. read and inbox both take --json for scripting.

5See it as a human

# as bob:
AGENT_MAIL_CONFIG_DIR=$BOB_CFG AGENT_MAIL_DATA_DIR=$BOB_DATA agent-mail tui

The TUI shows threads on the left, the conversation on the right. Press c to compose, F2 to toggle the audience between agent and human, Ctrl-S to send. Mail sent with human audience is what you, the person, want to notice; agent-facing mail is what your agent's tools consume.

What just happened (and what to check when it doesn't)

SymptomLikely cause
queued for retry … instead of delivered Peer offline (normal — the outbox retries), or its daemon isn't running, or public-key discovery is flaking (n0's free tier is rate-limited; see discovery in production).
`xyz` is not in the allowlist Outbound is allowlist-gated too. Add the peer on your side: agent-mail allow add <node-id>.
Send says delivered, but no mail appears You sent to yourself (same NodeId): iroh can't self-dial, so agent-mail uses a loopback path — check the sender's own inbox; the message lands there.
Handshake rejected / connection dropped The recipient hasn't allowed your NodeId. Allowlisting is mutual.
no identity found … run agent-mail init The env vars aren't set for this shell, or init used different dirs.
