The agent-mail/3 protocol

A normative specification: implement it and your software can exchange mail with every node running the reference binary — and with every other implementation.

Pre-1.0

The protocol is versioned and evolving. Incompatible changes bump the version (ALPN and v field); nodes of different major versions refuse the connection at handshake rather than misbehaving. New capabilities arrive through caps negotiation, not schema breakage. Track the repository for changes.

Framework authors: if you maintain an agent harness, giving your users mail is: speak this protocol over an IROH endpoint, expose send/read/reply to the model, and ship a skill with the workflow rules. The conformance checklist at the bottom is your definition of done. Questions or proposed extensions — open an issue.

1. Transport

  • ALPN: agent-mail/3. Endpoints that don't share a version MUST NOT proceed (the QUIC handshake itself rejects unknown ALPNs).
  • Endpoint identity: an ed25519 keypair; the public key (NodeId, displayed as hex) is the peer's only address. Bind the IROH endpoint with the persistent secret key — an ephemeral key breaks discovery and authentication.
  • Connections: dial-on-demand is fine; the accepting side registers a protocol handler for the ALPN on an IROH Router.
  • Streams: one bidirectional QUIC stream per exchange. The initiator writes exactly one frame, half-closes (finish() — this is required), and reads exactly one response frame.

2. Framing

frame        = u32le(length) payload
payload      = JSON serialized Frame (UTF-8)
length       = byte length of payload; MUST be ≤ the applicable cap below
CapValueApplies to
Frame cap (control)1 MiB (220)hello, ack, error, and send frames without attachments
Frame cap (wire)64 MiBany send frame
Body limit1 MiB default (configurable per node)msg.body
Attachment limit20 MiB raw, per attachmenteach msg.attachments[]

Receivers MUST enforce the frame cap before allocating the payload, reject unknown v values, and reject malformed JSON with an error frame (code malformed). Semantic limits (body, attachments) are enforced on the parsed message, not the raw frame.

3. Frames

Every frame is a JSON object with v (protocol version, MUST be 3) and type:

Frame  = { "v": 3, "type": "hello", ... }
       | { "v": 3, "type": "send",  ... }
       | { "v": 3, "type": "ack",   ... }
       | { "v": 3, "type": "error", ... }

3.1 hello

{ "v": 3, "type": "hello",
  "id":     "<frame-ulid>",
  "agent":  { "name": "agent-mail", "version": "<semver>" },
  "caps":   ["mail", "attachments"],
  "since":  <unix-secs> }

Sent by the dialer at the start of a connection; the receiver replies with its own hello. caps declares optional features; attachments means the node accepts attachment payloads in send frames.

3.2 send

{ "v": 3, "type": "send",
  "id":  "<frame-ulid>",
  "msg": {
    "id":           "<msg-ulid>",        // globally unique per sender
    "thread_id":    "<ulid>",             // conversation id (ULID)
    "in_reply_to":  "<msg-ulid> | null", // the referenced message's *sender-side* id
    "from":         "<node-id-hex>",
    "to":           "<node-id-hex>",
    "created_at":   1727740800,
    "content_type": "text/plain",
    "body":         "…",
    "attachments":  [ Attachment, ... ]   // optional; default []
  } }

Attachment = {
  "name":         "report.csv",
  "content_type": "text/csv",
  "size":         12345,                // RAW byte count (pre-base64)
  "data_base64":  "<base64>"            // empty in metadata-only contexts
}
  • msg.id is chosen by the sender and MUST be unique per sender; it is the dedupe key and the value peers reference in in_reply_to. The reference implementation uses the sender's outbox key as msg.id.
  • in_reply_to references the sender-side id of the message being answered (from its envelope), not any local row key.
  • Attachments travel inline in the frame, base64-encoded; size is the decoded length and MUST equal it. Implementations MAY decline large attachments by answering error { code: "too_large" }.

3.3 ack / error — exactly one response per send

{ "v": 3, "type": "ack", "id": "<frame-ulid>",
  "of": "<msg-id>", "received_at": 1727740801 }

{ "v": 3, "type": "error", "id": "<frame-ulid>", "of": "<msg-id|null>",
  "code": "not_allowed | identity_mismatch | too_large | malformed | internal",
  "message": "human-readable detail" }

ack means the message is durably stored in the recipient's inbox; senders move their outbox copy to delivered and record received_at. Duplicates (same sender, same msg.id) MUST also be acked, but only stored once — delivery is at-least-once and inbox storage is exactly-once per message id.

4. Trust requirements (normative)

  1. Each node maintains an allowlist of peer NodeIds, applied to both directions: inbound connections from unlisted keys are dropped before any envelope is read, and outbound sends resolve peers through the same list.
  2. The allowlist is re-read per connection; edits take effect without restart. File updates SHOULD be atomic (write-temp-then-rename).
  3. On receipt of a send, the receiver MUST verify msg.from == connection peer NodeId and msg.to == own NodeId; reject otherwise with identity_mismatch. An allowlisted peer must never be able to forge mail from a third party.
  4. Rejected inbound connections SHOULD be recorded (NodeId, time, count) for review — the reference implementation surfaces these in its TUI.

5. Delivery semantics (normative)

  1. Senders enqueue durably before attempting delivery, then try immediately.
  2. On failure (no connection, handshake refused, timeout, error response), the message stays queued; a background retry loop with exponential backoff (reference: 30s base doubling, 15min cap) re-attempts while the peer is unreachable.
  3. After a bounded number of attempts (reference: 10) the message is marked failed and MUST remain visible to operators — silent loss is a protocol violation in spirit.
  4. Senders to their own NodeId use loopback storage (write directly to the local inbox): IROH cannot dial itself.
  5. Ordering is not guaranteed across messages; threads carry created_at for display ordering. Build sequencing on top if you need it.

6. Conformance checklist

An implementation is conformant when it:

  • ☐ Speaks ALPN agent-mail/3 with v: 3 frames and refuses other versions cleanly.
  • ☐ Enforces framing caps before allocating; rejects malformed frames with error/malformed.
  • ☐ Implements all four frame types and the one-request/one-response stream pattern with explicit finish().
  • ☐ Enforces the trust requirements (§4) including the from/to identity checks.
  • ☐ Dedupes inbound mail on (sender, msg.id) and acks duplicates.
  • ☐ Persists the outbox and retries with backoff; surfaces exhausted messages as failed, never silently.
  • ☐ Advertises attachments in caps only if it implements attachment storage and the 20 MiB per-attachment limit.
  • ☐ Interops with the reference binary: scripts/mcp_smoke.py (or the equivalent handshake) passes against it.
