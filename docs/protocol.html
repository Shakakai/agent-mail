agent-mail Why Quickstart Production Agent harnesses Protocol Reference

Protocol & security model

agent-mail/2: length-prefixed JSON frames over IROH QUIC streams. Simple enough to reimplement, strict enough to trust.

Transport guarantees

Everything rides on IROH:

  • Authentication — the peer's ed25519 public key (NodeId) is verified by the QUIC/TLS handshake. There are no certificates and no unauthenticated connections: the NodeId you dial is exactly the key that answers.
  • Encryption — all traffic is end-to-end encrypted to the recipient's key.
  • NAT traversal — direct paths via hole punching, relay fallback when they fail. No inbound ports required.

Framing

u32 little-endian length N  (N ≤ 1 MiB by default)
N bytes of JSON: {"v": 1, "type": <frame>, ...}

One bidirectional stream per exchange: the initiator writes exactly one frame, half-closes, and reads exactly one response frame. Receivers enforce the frame-size limit before allocating; unknown protocol versions and malformed JSON are rejected with an error frame.

Frames

FrameFieldsMeaning
hello id, agent{name,version}, caps[], since Capability announcement at the start of a connection.
send id, msg A message (below). The sender's msg id is its outbox key — peers dedupe retries on it.
ack id, of, received_at Message stored in the recipient's inbox. Sent even for duplicates.
error id, of?, code, message Rejection: not_allowed, identity_mismatch, too_large, malformed, internal.

The message object

{
  "id":         "01H…",            // sender-chosen, unique per sender (ULID)
  "thread_id":  "01H…",            // conversation id (ULID, sender-chosen)
  "in_reply_to":"01H…" | null,     // the referenced message's *sender-side* id
  "from":       "<node-id>",
  "to":         "<node-id>",
  "created_at": 1727740800,
  "content_type":"text/plain",
  "body":       "…"
}

On receipt, the daemon enforces: from must equal the connection's peer key, to must equal this installation's key. Messages failing either check are rejected with identity_mismatch — an allowlisted peer cannot forge mail from a third party.

Trust model

  • Allowlist, both directions. Inbound connections from NodeIds not in allowed-keys.toml are dropped before any envelope is exchanged; the attempt is recorded in the rejections table. Outbound sends resolve peers through the same list, so a missing entry fails fast with a clear error.
  • Live updates. The list is re-read per connection: adding or removing a peer takes effect immediately, no daemon restart.
  • Human-gated changes. MCP-exposed trust changes (allow_add) are disabled unless mcp_allow_trust_changes = true.
  • Self-send. A NodeId is implicitly trusted to send to itself via a loopback path (iroh cannot dial its own NodeId): the message is written directly into the local inbox. Same policy checks (size limits) still apply.

Delivery semantics

  1. Send paths validate allowlist + size, write to the local outbox (direction='out'), and attempt immediate delivery.
  2. On ack, the outbox row is marked delivered with the recipient's received_at. The recipient stores an direction='in' copy.
  3. On failure, the daemon retries with exponential backoff (base 30s doubling, capped at 15min; the first retry is scheduled at enqueue so the interactive attempt and the daemon never race).
  4. After 10 attempts the row is failed — terminal, but visible: agent-mail outbox, the TUI status bar, and MCP list_outbox report it. Silent loss is treated as a bug.

Dedupe: recipients dedupe on (sender, sender's msg id) — retries, double-deliveries, and daemon/interactive overlap collapse to one inbox row. Net guarantee: at-least-once, at-most-one-inbox-row.

Ordering: messages are independent datagrams; threads carry created_at for display ordering. Do not build ordering-sensitive protocols on top without sequence numbers of your own.

The store

One SQLite database (WAL mode, busy timeouts) shared by the daemon, MCP server, TUI, and CLI on an installation. Single-writer processes coordinate through SQLite; mail survives any process restart, and the outbox is what makes offline peers workable. Files are owner-only (0600) and created atomically where corruption would be security-relevant (the allowlist).

Known limits

  • Public discovery is n0's free tier — rate-limited, no uptime SLA (mitigations: tickets / self-hosted DNS).
  • Plaintext bodies at rest (transport is encrypted; the local store is not) — protect the data directory.
  • One identity per installation; two endpoints sharing a key (e.g. standalone daemon and an MCP session) make discovery records flap — pick one mode per identity.
  • Messages are capped at 1 MiB by default — mail, not a file transfer protocol.
