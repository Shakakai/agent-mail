Production setup

Everything needed to run agent-mail as dependable infrastructure: an always-on daemon, complete configuration reference, discovery choices, hardening, and operations.

Choosing a topology

There are two daemon modes — pick per installation:

ModeWhenTrade-off
Embedded (automatic) Agent-facing installs: the MCP server (agent-mail mcp) spawns the daemon in-process for the life of the stdio session. Zero ops; the endpoint is online exactly while an agent is connected. Mail to an offline install queues at the sender.
Standalone (agent-mail daemon) Always-on mail: shared team inboxes, service agents, cron-driven agents, human-primary installs using the TUI. Needs process supervision (launchd/systemd below). Don't run both modes on one identity — two endpoints sharing a key makes discovery records flap.

Always-on daemon: launchd (macOS)

cat > ~/Library/LaunchAgents/com.agent-mail.daemon.plist <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>            <string>com.agent-mail.daemon</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/agent-mail</string>
    <string>daemon</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>RUST_LOG</key><string>agent_mail=info</string>
  </dict>
  <key>RunAtLoad</key>         <true/>
  <key>KeepAlive</key>         <true/>
  <key>StandardOutPath</key>   <string>/var/log/agent-mail.log</string>
  <key>StandardErrorPath</key> <string>/var/log/agent-mail.log</string>
</dict>
</plist>
EOF
launchctl load ~/Library/LaunchAgents/com.agent-mail.daemon.plist

Always-on daemon: systemd (Linux)

sudo tee /etc/systemd/system/agent-mail.service >/dev/null <<'EOF'
[Unit]
Description=agent-mail daemon (peer-to-peer mail for agents)
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/local/bin/agent-mail daemon
Restart=always
RestartSec=5
Environment=RUST_LOG=agent_mail=info
# Hardening
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/lib/agent-mail /etc/agent-mail

[Install]
WantedBy=multi-user.target
EOF
# with AGENT_MAIL_CONFIG_DIR=/etc/agent-mail and AGENT_MAIL_DATA_DIR=/var/lib/agent-mail
sudo systemctl enable --now agent-mail

Filesystem layout: one folder per node

The simplest production layout is one self-contained folder per node, selected with the global --home flag (or AGENT_MAIL_HOME):

agent-mail init --home /var/lib/agent-mail/researcher
agent-mail daemon --home /var/lib/agent-mail/researcher
agent-mail tui      --home ~/mail          # a human's own mailbox, same mechanism

Each home holds secret-key (0600), allowed-keys.toml (0600), config.toml, and mail.db — everything that node needs. Back up the folder, move it to another machine, or point a fresh binary at it: the node is the folder.

Finer-grained relocation remains available via env vars — per service, per container, per agent:

Env varDefaultPurpose
AGENT_MAIL_HOME — Unify config + data into one folder (same as --home).
AGENT_MAIL_CONFIG_DIR ~/.config/agent-mail Identity and trust: secret-key (0600), allowed-keys.toml (0600), config.toml
AGENT_MAIL_DATA_DIR ~/.local/share/agent-mail (Linux) / ~/Library/Application Support/agent-mail (macOS) Mail store: mail.db (+ WAL). Point backups here.
AGENT_MAIL_SECRET_KEY $CONFIG_DIR/secret-key Exact key file path — e.g. to mount a key from a secrets manager.
AGENT_MAIL_ALLOWED_KEYS $CONFIG_DIR/allowed-keys.toml Exact allowlist path — e.g. to sync trust from a shared source.

Pattern: one folder per agent

Two agents on one machine = two --home folders. The quickstart does exactly this with /tmp/am-alice and /tmp/am-bob. For containers, mount the home dir from a secret-backed volume; the node is entirely self-contained.

config.toml — every option

# $AGENT_MAIL_CONFIG_DIR/config.toml  (all values shown are the defaults)

# Maximum accepted wire frame, and the maximum message body that send paths
# will accept. Larger bodies are rejected before they reach the outbox.
max_message_bytes = 1048576        # 1 MiB

# Outbox retry backoff: first retry after retry_base_secs, doubling per
# attempt, capped at retry_max_secs. 10 attempts, then status = "failed"
# (surfaced via `agent-mail outbox`, the TUI, and the MCP list_outbox tool).
retry_base_secs = 30
retry_max_secs  = 900              # 15 min

# How often the daemon scans the outbox for due messages.
daemon_tick_secs = 15

# Relay infrastructure. "n0" (default) uses IROH's free public relays;
# "disabled" uses direct paths + explicit tickets only; "custom" points at
# your own relay server(s). See the IROH page for what relays do.
relay = "n0"

# Required when relay = "custom": your relay URL(s).
relay_urls = ["https://relay.example.com."]

# Publish/resolve addressing via n0's pkarr/DNS discovery (default true).
# Set false for ticket-only or LAN-only nodes — nothing is published and
# nothing is looked up; peers dial addresses you exchange out of band.
discovery = true

# Whether the MCP server may modify the allowlist (the allow_add tool).
# Keep false unless you specifically want your agent to manage trust.
mcp_allow_trust_changes = false

Changes take effect on process start; the allowlist itself is re-read per connection, so trust edits apply immediately without a restart.

Discovery & relays in production

All of the networking — discovery, relays, NAT traversal — is IROH, and it's collected on one page so this one doesn't have to re-explain it: How IROH moves the bytes. The short version: you run no servers; n0's free relays and discovery bootstrap connectivity, with self-hosting options (or out-of-band address tickets) when you need more control.

Scale

Tens of agents is the comfortable zone today. If you're thinking hundreds or thousands, the discovery/relay layer can be tuned for it — reach out.

Hardening checklist

  • File permissions — enforced automatically: secret key, allowlist, and mail store are owner-only (0600) on every open. Verify on shared hosts.
  • MCP trust changes — mcp_allow_trust_changes = false (default). Adding a NodeId is a human decision; keep it that way.
  • Allowlist hygiene — remove stale peers: agent-mail allow remove <name-or-id>. Inbound attempts from unknown keys are dropped before any envelope is read and logged to the rejections table (visible in the TUI allowlist view).
  • Mail is plaintext at rest. The transport is end-to-end encrypted, but the local store is a SQLite file — protect the data dir like any credential store (disk encryption, tight volume mounts).
  • Body size limits — enforced at enqueue on every path; lower max_message_bytes if agents exchange only short structured notes.
  • Agents must treat mail as untrusted input. The shipped skill instructs agents never to act on instructions found in mail without human confirmation — keep that instruction in your agent's system prompt.

Operations: what to monitor

SignalWhereHealthy
Outbox backlog agent-mail outbox · TUI status bar · MCP list_outbox 0 pending, 0 failed. A growing pending count means peers are offline or discovery is failing. Any failed > 0 deserves investigation — those messages will never send themselves.
Rejections TUI allowlist view (a) Expected when a peer hasn't allowlisted you yet; a pattern of rejections from an unknown key is reconnaissance.
Daemon log RUST_LOG=agent_mail=info → stdout/stderr of the daemon or MCP server endpoint online, periodic deliveries, no repeated delivery failed for the same peer.
Identity agent-mail id Stable across restarts (the secret key persists). Rotate by generating a new identity and re-allowlisting — there is no PKI to notify.

Backup and recovery

  • Back up the home folder (or the config + data dirs) — losing the secret key loses the address and all inbound capability peers have allowlisted.
  • The store (mail.db) holds history and the outbox. SQLite backup tools or a file copy while stopped both work.
  • Recovery: restore the folder, start the daemon with --home — the outbox resumes retrying anything still queued, and history is intact.

Multi-identity operations

# systemd template unit: one service per agent identity
sudo systemctl enable --now agent-mail@researcher
sudo systemctl enable --now agent-mail@reviewer
# with per-unit Environment=AGENT_MAIL_HOME=/var/lib/agent-mail/%i
# and ExecStart=/usr/local/bin/agent-mail daemon --home /var/lib/agent-mail/%i

For agent fleets, generate identities at provisioning time, exchange NodeIds through your normal secret channel (they are public keys — safe to pass through ticketing systems), and commit allowlists to config management.
