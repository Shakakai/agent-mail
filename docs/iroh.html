How IROH moves the bytes

agent-mail doesn't do its own networking. It rides on IROH — an open-source, public-key networking stack. This page collects everything about the transport in one place, so the rest of the docs don't have to care.

What IROH gives you

IROH conceptWhat it means for your agents
NodeId Every endpoint has a globally unique ed25519 public key. That key is the address — which is why agent-mail can say "exchange public keys" and be done with addressing forever.
Authenticated, encrypted connections The QUIC/TLS handshake proves the peer holds the private key for the NodeId you dialed, and encrypts everything to it. No certificates, no PKI, no identity surprises.
NAT traversal & hole punching Two agents behind home or office NATs find each other and open a direct path. This is why "a laptop and a cloud VM" is not a special case.
Relays When direct paths can't be established, traffic flows through a relay. IROH's free public relays (operated by n0) cover this out of the box; you can run your own.
Discovery (pkarr/DNS) A NodeId resolves to current dialing info via published records. n0's free discovery works for development and small deployments; production options below.

The honest model: what runs where

You run no servers

There is no agent-mail server anywhere in the system. The only always-on piece is each node's own daemon, on hardware you choose. The relays and discovery that make "dial any NodeId on Earth" practical are operated as a free public service by n0 (the team behind IROH) — open source, replaceable, and self-hostable.

In concrete terms, when your agent dials a peer for the first time: discovery resolves the NodeId to addressing hints, the endpoints negotiate through their NATs (with relay help if needed), and once a direct path exists, traffic flows peer-to-peer. First contact can take a few seconds; reconnects are fast. None of this is agent-mail code — it's IROH, and it behaves the same for the reference binary and for anything you implement yourself against the protocol.

Discovery & relays in production

  1. Tickets (bypass discovery entirely). Exchange an address out of band and dial it directly: 
    # recipient:
agent-mail addr > ticket.json
# sender:
agent-mail send bob --ticket "$(cat ticket.json)" -m "…"
    Ideal for LANs, VPCs, and anywhere you control both ends.
  2. Self-host relays (and discovery). Run your own relay and point the node at it — two lines in config.toml: 
    relay = "custom"
relay_urls = ["https://relay.example.com."]
    For strict environments also run your own pkarr/DNS (the IROH docs cover iroh-dns-server); until then you can keep n0 discovery or set discovery = false and use tickets.
  3. Use the free tier, eyes open. n0's discovery is rate-limited and has no uptime SLA; it flaps occasionally. The outbox's retry loop absorbs most of it — watch your failed count (see operations).
  4. Skip relays entirely. relay = "disabled" plus discovery = false gives you a node that makes no outbound infrastructure connections at all — direct LAN paths and address tickets only. (The daemon knows not to wait for a relay connection in this mode.)

Transport limits that matter to mail

  • First-contact latency is discovery-dependent; queued mail hides it.
  • Connections are peer-to-peer QUIC streams — large attachments move fine, but mail is still not a bulk file-transfer protocol.
  • An endpoint's reachability while offline is zero — that's what the persistent outbox is for.
