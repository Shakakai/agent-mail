Mail for agents.
No servers. No accounts. No portals.

agent-mail gives every AI agent a mailbox with a cryptographic address. Agents exchange messages directly over IROH — authenticated by ed25519 public key, end-to-end encrypted, NAT-traversed — while humans read and write the same mail through a TUI, CLI, or their agent's chat.

Why agents need mail

Multi-agent systems today communicate through whatever the orchestrator happens to pass along: prompt context, shared files, database rows, or bespoke HTTP callbacks. Each integration is one-off, unencrypted, unaudited, and invisible to the human who is ultimately responsible. agent-mail replaces that sprawl with one mechanism that has worked for humans for decades — mail — adapted to agents:

  • Addressable by construction. An agent's address is its public key. There is nothing to register, renew, or squat. If you know the key, you can send; if the recipient allows your key, it receives.
  • Asynchronous by design. Peers are offline more often than they are online. Mail queues in a persistent outbox and retries with backoff — an agent on a laptop, a cron job, or a CI runner can all receive mail without a public endpoint.
  • Trust you can reason about. Both directions are gated by an explicit allowlist of NodeIds. There is no unauthenticated state to defend: a peer is either on the list or it is dropped, and rejections are recorded and visible.
  • Humans get their own mailbox. A person runs their own node — own private key, own --home folder, own TUI — and agents address them like any peer. No shared stores, no mixed inboxes.
  • Auditability for free. Every message lands in a local SQLite store: threads, delivery status, retries, and failures are queryable — by the agent's tools and by the human's terminal alike.

Each installation runs one identity, one store, and — while an agent is connected — one embedded daemon that owns the IROH endpoint. The MCP server is the agent interface; the TUI and CLI are the human interfaces. Everything reads and writes the same mail.

Built for AI engineers

ConcernHow agent-mail handles it
Identity ed25519 keypair, generated locally by agent-mail init. The NodeId is the address — verified by the QUIC/TLS handshake itself, not by a certificate.
Connectivity IROH handles NAT traversal, hole punching, and relay fallback. No open ports, no DNS records, no VPN. Works across home NATs, cloud VMs, and laptops.
Offline peers Persistent outbox with exponential backoff (30s → 15min). After 10 attempts a message is marked failed and stays visible — silent loss is a bug, not a feature.
Agent integration A stdio MCP server with 9 tools (send, reply, inbox, threads, outbox, identity, allowlist) plus a subscribable agent-mail://inbox resource for push-style notification. Ships with a ready-made skill for agent instructions.
Human integration ratatui TUI with threads, compose/reply, allowlist editor, and rejection log; every TUI action has a CLI equivalent for scripting.
Security model Allowlist gates both directions and is re-read per connection. Secret key is 0600; mail store files are owner-only. Trust changes via MCP are disabled by default.
Ops Single static binary, no runtime dependencies. Config via one TOML file and four env vars. Runs as a foreground daemon, an embedded per-session daemon, or a launchd/systemd service.

When mail — and when not

agent-mail is the right tool when:

  • two or more agents (or an agent and a human) need to hand off work, ask questions, or report results without sharing a host or an orchestrator;
  • peers come and go (laptops, spot instances, scheduled jobs) and you need store-and-forward semantics;
  • you want a durable, queryable record of what agents told each other.

It is deliberately not a RPC framework: delivery is at-least-once, messages are plain text, and "queries" are conversations, not synchronous call/response. For millisecond-latency fan-out inside one process, keep your function calls; use mail at the trust and availability boundaries.
